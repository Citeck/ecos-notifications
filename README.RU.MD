# `ecos-notifications`

**На других языках: [Английский](README.md)**

Добро пожаловать в репозиторий Citeck `ecos-notifications`! Репозиторий содержит шаблоны уведомлений и конфигурации для платформы Citeck — системы для автоматизации бизнес-процессов и управления корпоративными данными.

## Начало работы

Если вы впервые знакомитесь с платформой Citeck и хотите запустить программное обеспечение локально, мы рекомендуем загрузить Docker-версию из [Demo-репозитория](https://github.com/Citeck/citeck-community).

## Зависимости

Для запуска этого приложения необходимы следующие компоненты из развертывания Citeck:

* zookeeper
* rabbitmq
* ecos-model
* ecos-registry

## Разработка

Для запуска notification-app в режиме разработки с подключением к локальному SMTP-серверу (например, MailHog порт 1025), запустите приложение с профилями:

- dev
- dev_local

Если запуск выполняется на macOS, добавьте профиль:

- dev_local_macos

Для запуска с реальным SMTP-сервером см. пример [application-dev_smtp_gmail.yml](src/main/resources/config/application-dev_smtp_gmail.yml)

выполните:

```
./mvnw spring-boot:run
```

Если ваша IDE поддерживает прямой запуск Spring Boot-приложений, вы можете просто запустить класс 'ru.citeck.ecos.notifications.NotificationsApp' без дополнительных настроек.

### Сборка для production

Для сборки приложения в production-режиме выполните:

```
./mvnw -Pprod clean package jib:dockerBuild -Djib.docker.image.tag=custom 
```

Чтобы убедиться, что всё работает, остановите оригинальный контейнер ecos-notifications и запустите ecos-notifications:custom вместо него.

### Тестирование

Для запуска тестов выполните:

```
./mvnw clean test
```

#### Качество кода

Для анализа качества кода используется Sonar. Вы можете запустить локальный сервер Sonar (доступный по адресу http://localhost:9001) командой:

```
docker compose -f docker/sonar.yml up -d
```

Затем выполните анализ Sonar:

```
./mvnw -Pprod clean test sonar:sonar
```

## Настройка повторных отправок

Уведомление, которое не удалось отправить, повторяется по каждой строке отдельно с экспоненциальной
задержкой:

```yaml
ecos-notifications:
  retry:
    enabled: true         # false => первая же ошибка сразу финальная; ручной повтор продолжает работать
    poll-interval: 30s    # как часто задание ищет уведомления, готовые к повтору
    batch-size: 50        # сколько уведомлений берётся за один проход, ограничивает нагрузку после сбоя
    max-attempts: 20      # страховочный предел, основное ограничение — retry-window
    initial-interval: 1m  # задержка перед первым повтором, далее умножается на каждой попытке
    multiplier: 3.0
    max-interval: 2h      # максимальная задержка между попытками
    retry-window: 24h     # отсчитывается от первой ошибки уведомления
    lease-time: 15m       # на сколько взятая пачка закрепляется за одним экземпляром сервиса
```

Статусы уведомлений:

* `ERROR` — последняя попытка не удалась, следующая запланирована
* `SENT` — доставлено (возможно, части получателей — остальные перечислены в сообщении об ошибке)
* `FAILED` — неустранимая ошибка (некорректный адрес, сломанный шаблон, некорректная конфигурация
  отправителя): повтор не поможет, поэтому делается ровно одна попытка
* `EXPIRED` — исчерпан бюджет повторов (`max-attempts` или `retry-window`)

Уведомления в статусах `FAILED`, `EXPIRED` и `ERROR` можно вернуть в очередь повторных отправок из
журнала уведомлений (действие «Повторить отправку»), при этом бюджет повторов сбрасывается.

### Переход с `error-notification`

Блок `ecos-notifications.error-notification` устарел. Заданные в нём значения по-прежнему принимаются
(чтобы существующие стенды продолжали запускаться), но **игнорируются**, а при старте пишется WARN.
Соответствие настроек:

| было                                 | стало                                                                   |
|--------------------------------------|-------------------------------------------------------------------------|
| `error-notification.delay`           | `retry.poll-interval` и настройки задержки между попытками               |
| `error-notification.ttl`             | `retry.retry-window` (от первой ошибки, а не от создания уведомления)    |
| `error-notification.ttl: -1`         | больше не поддерживается — повторы всегда ограничены                     |
| `error-notification.min-try-count`   | `retry.max-attempts` (теперь это верхняя граница, а не нижняя)           |

Изменения в поведении:

* уведомления с неустранимой ошибкой больше не отправляются повторно — они попадают в новый статус
  `FAILED` после единственной попытки, поэтому его нужно учесть в дашбордах и журналах
* значения `spring.mail.properties.mail.smtp.*timeout` должны оставаться конечными, а
  `mail.smtp.sendpartial` включён, чтобы письмо, отклонённое для части получателей, всё же
  доставлялось остальным
* для мониторинга доступны метрики `notifications.retry.attempts`, `notifications.retry.terminal`
  и `notifications.retry.backlog`
